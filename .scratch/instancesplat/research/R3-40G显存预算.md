# R3 — 8×A100 40G 单卡显存预算

> 票：`.scratch/instancesplat/tickets/R3-40G显存预算.md`
> 目标配置：`anysplat` + `instance_feat_dim: 8` + `voxelize: true, voxel_size: 0.002`，
> **backbone 全量微调**，1 场景 × 最多 8 视角 × 448×448，`precision: bf16-mixed`，DDP over 8 卡。

> **本机无 Python 环境、无 GPU**，全部数字来自「读代码 + 公开数字 + 手算」。

## 0. 结论先行

| | 值 |
|---|---|
| **现状（不改任何代码，8 视角 @448）峰值** | **44–52 GB** ⇒ **在 40G 上 OOM，缺口约 6–14 GB** |
| **开齐「零代码/低代码」开关后** | **30–36 GB** ⇒ 8 视角勉强能跑，但余量 < 6 GB，Gaussian 数量波动就能打爆 |
| **再加上 DPT 头的梯度检查点（需新代码）** | **23–29 GB** ⇒ 8 视角 @448 舒适可行 |
| **不想写新代码时的安全配置** | **6 视角 @448**（约 26–30 GB） |
| A100-40GB 实际可用 | 40536 MiB ≈ **39.6 GiB ≈ 42.5 GB**，扣 CUDA context/NCCL 后**预算按 38 GB 算** `[公]` |

**最关键的那个开关**：**给四个 DPT 栈（`depth_head` / `point_head` / `gaussian_param_head` / `PartHead`）加梯度检查点**。
仓库里 checkpointing **只在 aggregator 和 DINOv2 上开着**，四个 DPT 栈**一个都没有**，
而它们合计占激活的 **~18 GB / 24 GB**。

**但比显存更要命的一个发现**见 §6：`src/model/arch/anysplat.py:124` 把 aggregator 永久转成
**bf16 参数**，AdamW 在 bf16 主权重上的更新量会被舍入成 0 ——「backbone 全量微调」很可能是空转。

## 2. 8 视角是不是**必须**开梯度检查点

**必须，而且必须开在目前没开的地方。**

仓库里现成的 checkpointing 开关（都是**硬编码 True，没有配置字段**）：

| 位置 | 状态 |
|---|---|
| `src/model/vggt/models/aggregator.py:71` `self.use_checkpoint = True` → `:300`、`:328` | ✅ 已开（frame + global 共 48 块）|
| `src/model/vggt/layers/vision_transformer.py:97` → `:244`、`:271` | ✅ 已开（DINOv2 24 块）|
| `src/model/vggt/heads/camera_head.py:137` | ✅ 已开 |
| `src/model/segvggt/models/aggregator.py:569,592,631,707` | ✅ 已开（但 SegVGGT 路线不在本 effort 内）|
| `src/model/vggt/heads/dpt_head.py` | ❌ **没有** |
| `src/model/heads/gaussian/vggt_dpt_gs_head.py` | ❌ **没有** |
| `src/model/heads/instance/part_head.py` | ❌ **没有** |
| `src/model/heads/instance/sam_projector.py` | ❌ **没有** |

（`grep -n "checkpoint" src/model/vggt/heads/dpt_head.py src/model/heads/gaussian/vggt_dpt_gs_head.py src/model/heads/instance/*.py` 只命中 part_head.py:207 的一句英文注释。）

也就是说：**transformer 那 909M 参数的激活已经被压到 1.2 GB 了，而四个 DPT 栈没人管，
反而是激活大头（~18 GB）。** 检查点开在 aggregator 上是「已完成的工作」，
真正的空白在 head 侧。

### 一个常见误解要澄清：`frames_chunk_size` **在训练时不省显存**

`DPTHead.forward(..., frames_chunk_size: int = 8)` `[码 dpt_head.py:133]` 和
`VGGT_DPT_GS_Head.forward(..., frames_chunk_size: int = 8)` `[码 vggt_dpt_gs_head.py:41]`
会在 `S > frames_chunk_size` 时分块前向再 `torch.cat`。
**但每块的激活都要留着给 backward**，`cat` 之后总量不变 —— 它只降低推理时的瞬时峰值，
训练时**一点也不省**。想省必须是「分块 + 每块 `torch.utils.checkpoint`」。
（S=8、默认 8 时它根本不分块。）

## 3. 高斯数量与两路渲染

### 3.1 体素化到底压缩多少 —— 取决于什么

`voxelizaton_with_fusion` `[码 anysplat.py:307-364]` 的核心只有一行：

```python
voxel_indices = (pts3d_flatten / voxel_size).round().int()   # anysplat.py:313
unique_voxels, inverse_indices, counts = torch.unique(voxel_indices, dim=0, ...)
```

然后按 `conf` 做 per-voxel softmax 加权求和（位置、GS 参数、实例特征三者共用同一套
`inverse_indices`，所以 `gaussian_instance_feat` 与 `gaussians` 行对齐 —— T1 票里那条已确认的事实）。

**关键点：`pts3d` 没有做任何尺度归一化就直接除以 `voxel_size`。**
`normalize_pts3d` 在体素化路径上**没被调用**；`scene_scale`（`anysplat.py:522`）只是被塞进
`infos` 打日志用。所以体素栅格的物理粒度 = `voxel_size` × VGGT 输出的那个坐标系的尺度。

VGGT 的训练归一化是「用**全部 3D 点到原点的平均欧氏距离**做尺度」，并且模型被训成
**直接在这个 canonical 空间里输出** `[公 VGGT CVPR'25 §3 Normalization]`。
所以 `voxel_size = 0.002` ≈ **场景平均点距的 1/500**。

对一个平均点距 ~2.5–3 m 的 ScanNet++ 房间：**1 voxel ≈ 5–6 mm** `[算]`。
而 448 px 覆盖 ~70–90° FOV 时，角分辨率 ≈ 3.1e-3 rad，
在 2 m 处的像素足迹 ≈ 6 mm、1 m 处 ≈ 3 mm、4 m 处 ≈ 12 mm `[算]`。

**⇒ 体素尺寸和像素足迹是同一量级。** 结论：

1. **单视角内几乎不压缩**：只有距离 < ~2 m 的近景表面会有多像素落进同一体素。
2. **压缩比几乎全部来自视角间重叠**：8 个视角看同一片墙 → 最多 8:1；8 个视角基线很宽、
   各看各的 → 接近 1:1。
3. **随深度分层**：近景压得狠、远景压不动。
4. 因此 `voxelize_ratio` **强依赖于 view sampler 的 `min/max_distance_between_context_views`**，
   T4 票改视角采样会直接改这个数。

**估计区间 `[算]`：`voxelize_ratio ∈ [0.16, 0.6]`，即 N ∈ [0.25M, 0.96M]；
硬上界 N = 1.606M（完全不压缩）。** 这是整张表里**不确定度最大的一项**。

好消息：**这个数仓库已经在打点了**，不用写新代码就能实测：
`infos["voxelize_ratio"] = densities.shape[1] / (h*w*v)` `[码 anysplat.py:645]`，
经 `self.log("train/voxelize_ratio", ...)` `[码 anysplat_wrapper.py:142]` 进 TB/wandb。

### 3.2 两路渲染的显存

RGB 路：`gsplat.rasterization(..., sh_degree=4, render_mode="RGB+D", packed=False)`，
**外层 Python 循环逐视角调用** `[码 decoder_splatting_cuda.py:77-88]`。

`Gaussians` 全部是 fp32 `[码 gaussian_adapter.py:135-143]`，
`sh_degree: 4` → `d_sh = 25`，`d_in = 7 + 75 = 82`，`raw_gs_dim = 83`（= 配置里的 `anchor_feat_dim: 83`）。

每个高斯的常驻字节 `[算]`：
`means 12 + covariances 36 + harmonics 300 + opacities 4 + scales 12 + rotations 16 = 380 B`，
加上 adapter 构造图（softplus/归一化/`broadcast_to*sh_mask`/`build_covariance`）≈ +500 B，
加上 `harmonics.permute(0,1,3,2).contiguous()` 的新拷贝 `[码 decoder_splatting_cuda.py:54]` +300 B。

每视角光栅化保存的（SH 求值 + 投影 conics/means2d/radii/depths + isect id 表）≈ 104 B/高斯 `[算]`，×8 视角。
实例特征路（T1，`sh_degree=None`、D=8）省掉 SH 求值但要重做一遍投影 ≈ 96 B/高斯，×8 视角。
D=8 远小于 gsplat 的 `channel_chunk=32`，**不会触发分块，也不落进「D>32 很慢」那条警告** `[公 gsplat rasterization 文档]`。

| N（高斯数）| Gaussians 对象 | adapter 构造图 | permute 拷贝 | RGB×8 | 特征×8 | **合计** |
|---|---|---|---|---|---|---|
| 0.25 M（ratio 0.16）| 0.10 | 0.12 | 0.07 | 0.21 | 0.20 | **0.70 GB** |
| 0.60 M（ratio 0.37）| 0.23 | 0.30 | 0.18 | 0.50 | 0.48 | **1.69 GB** |
| 1.61 M（ratio 1.0，上界）| 0.61 | 0.80 | 0.48 | 1.34 | 1.28 | **4.52 GB** |

量级校准 `[公 gsplat profiling]`：packed=False、batch 1、含 fwd+bwd 的 RGB 渲染约 **0.48 GB**，
32 通道特征图约 **0.61 GB**（garden 量级场景、单相机）。我们是 8 相机串行 + 两路，
落在同一量级，估算自洽。

**「两次调用 vs 拼进一次调用」的量化答案（回答 T1 票的决策 1）**：
第二次调用的净增量 ≈ `(96 B × 8 + 32 B) × N` ≈ **0.20 GB @0.25M / 0.48 GB @0.6M / 1.28 GB @1.6M**。
即使在最坏的 1.6M 上界，两次调用的代价也只有 **~1.3 GB**，
换来的是「不动 RGB 路径 = 不干涉既有实现」。**显存不构成反对两次调用的理由。**

## 4. 现状里几处「白交的学费」

### 4.1 `point_head` 被凭空多跑了一遍

`instseg_anysplat.yaml` 用 `pred_head_type: depth`，于是：

```python
# anysplat.py:138-142
self._use_point_head_for_part = (int(cfg.instance_feat_dim) > 0 and self.cfg.pred_head_type == "depth")
if self._use_point_head_for_part:
    self.point_head = model_full.point_head
```

→ **同时构造 `depth_head` 和 `point_head`**，前向里两个 DPT 栈都跑一遍
`[码 anysplat.py:471-484]`。代价：**+32.7 M 参数（0.52 GB 优化器）+ 1.53 GB 常驻激活
+ 4.2 GB 瞬时峰值 + 约 15–20% 的 head 计算时间**。

`pred_head_type: point` 本来能一次拿到 `pts_all` 和 `point_intermediate`，
但**这条路现在是坏的**：`point` 分支从不给 `depth_conf` 赋值，而

```python
# anysplat.py:496
conf_valid_mask = torch.ones_like(depth_conf, dtype=torch.bool)   # NameError
```

无条件引用它（`anysplat.py:490-496`，`depth_dict` 那行 `anysplat.py:663` 同理引用 `depth_map`）。
**这是一个 3 行的 bug fix，能换 ~2 GB + 一整个 DPT 前向。** 建议交给 T7 决定要不要修。

### 4.2 DPT 几何头跑在 fp32 里

`with torch.amp.autocast("cuda", enabled=False)` `[码 anysplat.py:438]` 把
`camera_head` + `depth_head` + `point_head` + pose 代数**整块**关掉了 autocast。
pose 代数确实需要 fp32（`git log` 里 `36a7889 fix(segvggt): keep geo pose algebra in fp32` 就是这个教训），
但 **DPT 的一堆 3×3 卷积不需要**。把 autocast 关闭窗口缩到只包住
`pose_encoding_to_extri_intri` + `batchify_unproject_depth_map_to_point_map`，
DPT 卷积走 bf16 → 省 **0.5 × (5.69 + 1.53) = 3.6 GB**。

### 4.3 LPIPS 也在 fp32 里

`anysplat_wrapper.py:181` 把整个 `compute_and_log_losses` 包进 `autocast(enabled=False)`，
LPIPS 的 VGG16 在 8×448×448 上跑 fp32 = **3.5 GB**。改 bf16 省 1.75 GB；
或只对 8 个视角里的 4 个算 LPIPS（论文没规定 LPIPS 打几个视角）再省一半。

### 4.4 `torch.cuda.empty_cache()` 每步调两次

`anysplat.py:430`（distill 分支，我们用不到）和 `anysplat.py:525`（每步都走）。
它降碎片、但**强制同步 + 把缓存块还给驱动**，下一次分配要重新 `cudaMalloc`。
在我们这种「每步 shape 都不同」（5 档宽高比 × 视角数 2–8 = 40 种形状）的场景里，
留着它是**对的**（碎片才是主要杀手），但要在耗时估计里给它记 50–200 ms `[算]`。

## 6. ⚠️ 比显存更严重的问题：bf16 主权重会把 backbone 的更新舍成 0

三条事实拼起来：

1. `src/model/arch/anysplat.py:124`：`self.aggregator = model_full.aggregator.to(torch.bfloat16)` ——
   aggregator 的 **909.1 M 参数被永久转成 bf16**。
   `load_state_dict` 用 `copy_` 保持目标 dtype，所以从 `hf:lhjiang/anysplat` 加载后**仍是 bf16**
   `[码 weight_loading.py:67]`。
2. Lightning 的 `precision="bf16-mixed"` **只是把 forward 包进 `torch.autocast`，不改参数 dtype、
   也不额外维护 fp32 master weights**（fp32 参数本身就是 master）`[公 Lightning MixedPrecision 源码 / N-Bit Precision 文档]`。
   ⇒ **票面上「bf16-mixed 下还要算 fp32 master weights」这条前提是错的** —— 没有额外的 master 副本；
   真正的问题反过来：aggregator 连 fp32 副本都没有。
3. AdamW 的更新量 ≈ `lr × m̂/(√v̂+ε)` ≈ `lr × O(1)`。配方里 transformer 层 lr = `2e-4 × 0.1 = 2e-5`。
   bf16 只有 8 位尾数（相对 eps `2^-8 ≈ 3.9e-3`），ViT-L 线性层权重典型量级 ~0.03
   ⇒ **ULP ≈ 1.2e-4，是更新量 2e-5 的 6 倍** `[算]`。
   ⇒ **绝大多数 backbone 权重更新在 `param.add_()` 时被舍入回原值。**

**含义**：现在这套代码即使显存够，「backbone 全量微调」也大概率等于「backbone 冻结」，
而 Table 3 的「3DGS frozen」消融（T-mIoU 58.86 vs 64.03）正是这次要避开的坑。

**三个选项**：

| 选项 | 显存 | 说明 |
|---|---|---|
| (a) aggregator 提回 fp32（删掉 `.to(torch.bfloat16)`，靠 autocast 拿 bf16 算力）| **+7.27 GB**（静态 12.7 → 20.0 GB）| 数值正确。**必须配 §5 第 2 项 ZeRO-1**，否则静态项就吃掉一半卡 |
| (b) 保持 bf16 参数 + 自建 fp32 master | 与 (a) 同量级（2+2+4+4+4 = 16 B/param）| 没有省 |
| (c) 保持现状 | 12.7 GB | **等于没在训 backbone**，与配方矛盾 |

**建议**：选 (a) + ZeRO-1，静态项 = **11.25 GB**（比现状的 12.7 GB 还低）。
这是本票最重要的一条结论。它需要在集群上用 §8 的探针 3 先证实，再由 T7 落地。

> 注：`anysplat.py:124` **不在**地图硬约束列表里（那四个是
> `instseg_anysplat.yaml` / `loss_disc.py` / `loss_mvc.py` / `config/model/encoder/anysplat.yaml`），
> 但它是 AnySplat / SegVGGT 共用的路径，改动要走「新增可选开关、默认保持原行为」的写法。

## 7. 「不行时先砍哪个」——有优先级的清单

先砍**不偏离论文**的，再砍偏离论文的；偏离项里先砍代价小的。

1. **加 DPT 梯度检查点**（−11~13 GB，不偏离论文，只是慢 ~10%）
2. **ZeRO-1 优化器分片**（−5.6 GB，不偏离论文，纯工程）
3. **`gradient_as_bucket_view=True`**（−3.2 GB，一行，不偏离论文）
4. **DPT 头改 bf16 / 修掉重复的 point_head / LPIPS 走 bf16**（−7.4 GB，不偏离论文的超参）
5. **视角数上限 8 → 6**（−6 GB）。**先砍视角数、不砍分辨率**，理由：
   - 论文 Table 1 显示 mIoU 对视角数**不敏感**（2/4/8/16 视角分别 65.23 / 43.51 / 58.76 / 64.60），
     视角数本来就是随机采样的增广维度，把上界从 8 降到 6 只是把分布截短；
   - 而 **448 是论文 Table 1 的评测口径**（"all metrics are computed at a resolution of 448×448"），
     训练分辨率一旦低于评测分辨率，PSNR/mIoU 都不可比，归因会断。
6. **长边 448 → 392**（−5.8 GB）。最后手段，且必须在票里写明评测仍在 448、
   存在 train/test 分辨率不匹配。**注意 384 不合法**（patch 14 不整除），别写进配置。
7. **冻结 camera_head**（−2.6 GB）。明确偏离论文，只在 1–6 都用尽还差最后几 GB 时用。

估算里最不确定的三项，都可以用**一次前向/几步训练**打掉。不在这里写脚本。

2. **分段峰值显存**（打掉 §1.2 的 ±25%）

## 9. 每步耗时与 10k steps 墙钟

### 9.1 FLOPs 自下而上 `[算]`

| 部分 | 前向 TFLOP | 反向倍数 | 合计 TFLOP |
|---|---|---|---|
| aggregator 线性部分（24 frame + 24 global + DINOv2 24，各 12.6M×2×8232 token）| 15.0 | ×4（checkpoint 要重算前向）| 60.0 |
| aggregator 注意力（frame 24×8×1029²；global 24×1×8232²，dim 1024）| 7.4 | ×4 | 29.6 |
| 四个 DPT 栈（refinenet1@128² 与 448² 的 tail 主导）| ~6 | ×3 | 18 |
| SamProjector + Swin 块 | ~0.9 | ×3 | 2.7 |
| LPIPS VGG16（pred+gt 前向，pred 反向）| ~1.0 | ×2 | 2.0 |
| **合计** | | | **≈ 112 TFLOP/step** |

A100-40GB SXM bf16 峰值 312 TFLOPS `[公]`；这种「注意力 + 大量高分辨率卷积 + 部分 fp32」
混合负载的实际 MFU 取 25–35% ⇒ 有效 80–110 TFLOPS ⇒ **纯计算 ≈ 1.0–1.4 s**。

加上：
- 两路 × 8 视角 = **16 次 `rasterization` 串行调用** `[码 decoder_splatting_cuda.py:77]`，
  按 gsplat profiling 的 fwd+bwd 量级 ≈ 15–30 ms/次 `[公]` ⇒ **0.25–0.45 s**；
- `torch.cuda.empty_cache()` `[码 anysplat.py:525]` ⇒ **0.05–0.2 s**；
- `find_unused_parameters=True` 的图遍历 `[码 main.py:105]` ⇒ **0.02–0.05 s**；
- DDP allreduce 3.2 GB（bf16 909M + fp32 341M）：NVLink/NVSwitch 节点 ~0.02 s（与 backward 重叠）；
  **纯 PCIe 节点可能 0.2–0.4 s 且难以重叠**；
- 数据加载（8 张图解码 + resize），应被 worker 掩盖。

### 9.2 结论

| | 值 |
|---|---|
| **8 视角 @448 的单步** | **2.0–3.5 s**（中位 ~2.5 s）|
| 视角数在 2–8 均匀随机（均值 5）⇒ 平均步 | **1.4–2.4 s**（中位 ~1.8 s）|
| **10k steps 墙钟（纯训练）** | **4–7 小时**（中位 **~5 小时**）|
| + 每 500 步一次 val（`limit_val_batches: 1`）| +10–20 分钟 |
| + checkpoint：`save_weights_only: false` + `save_top_k: 3` ⇒ 每份含**完整优化器状态 ~12.7 GB**，20 次保存 | **+20–40 分钟，且占 ~38 GB 磁盘**。建议 T7 把 `every_n_train_steps` 调大或改 `save_weights_only: true` |
| **总计** | **5–8 小时** |

**对照校准 `[公]`**：论文 4.1 说「Training is performed on 2×A800 GPUs with a batch size of 8 images…
1k warm-up + 20k cosine… Training completes in approximately 21 hours」
⇒ **3.6 s/iteration on 2×A800**。A800 与 A100 的 SM 数与 bf16 算力相同（只是 NVLink 带宽被限），
所以他们的 3.6 s 与我们估的 2.5 s（8 视角）/1.8 s（平均）在同一量级 —— **估算自洽**，
差异可由「他们只有 2 卡、allreduce 路径更长」和「他们没有 PartHead 之外的额外开销」解释。

> 顺带：论文的 "batch size of 8 images" 和本仓库 `data_sampler.py:208` 的
> `batch_size = max_img_per_gpu / random_image_num` 是同一个概念（每卡按总图片数配平）。
> 我们的 `max_img_per_gpu: 8` + 8 卡 = 每步 8 个场景，正好是论文 2 卡的 **4×**，
> 与地图里「有效 batch 4×、lr 1e-4 → 2e-4（sqrt scaling）」一致。
